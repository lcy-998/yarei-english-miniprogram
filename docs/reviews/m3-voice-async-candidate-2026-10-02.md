# M3 跟读异步评分候选差异（待产品审阅，2026-10-02）

> 历史候选，**尚未实施异步队列或云端配置**。2026-10-02 用户现已放宽原 15 秒硬门槛，保留 5 分钟录音并要求只在 CloudBase 云端运行/测试模型。本文件中的 15/30 秒对比保留为方案演变背景，具体试验超时应由云端冷/热启动、音频长度与套餐额度证据决定，不能把旧候选值当作新要求。

## 候选流程

1. 学生仍按 `beginRecording → sealRecording → beginScore` 上传并封存私有 MP3。`beginScore` 在当前学生、任务/阅读授权、句段快照、录音哈希、提交轮次与五次上限通过后，事务性创建 `processing` 评分作业并迅速返回 `scoreId`，不在客户端请求内等待 Python 完成。同一 `operationId` 重试只返回同一作业。
2. 可信服务端使用平台**真正的异步事件调用**派发 Python；[CloudBase 普通函数支持异步调用](https://docs.cloudbase.net/cloud-function/quickstart/select-types)，但现用 `@cloudbase/js-sdk` 的 `callFunction` 参数没有异步选项，须先在目标环境验证 SCF `Invoke` Event 或受控触发器能否由既有身份调用、是否产生新费用及队列延时，不能把 Node 内未 `await` 的 Promise 当作持久作业。Python 仍拒绝客户端直调、下载私有录音并验 SHA/大小；完整转写、URL 与令牌不得落日志。
3. Python 把签名回执交给受限 Node 完成入口。Node 在落库前**重新**检查学生状态与授权、任务发布快照、提交轮次、文件哈希、模型/算法版本、作业 lease 及当前正式提交状态；任何撤权、提交锁定或版本变化只记录失效，不把旧结果计入当前任务。结果由作业 ID 的 CAS 唯一落库。`scored` 才占一项有效次数，`unreliable`/系统失败不占次数；最近一次**有效**评分仍是任务候选结果，直到正式质量放行前都不计正式成绩/打卡。
4. 客户端每 2 秒轮询 `getScore`，回后台时停止轮询，重新打开 S-05 时用 `listAttempts` 找到 `processing` 作业恢复轮询；弱网调用失败保留本机与已封存录音，按同一操作 ID 恢复。服务端作业状态为 `processing | scored | unreliable | failed | superseded`，轮询查询只返回本人投影；教师仅能读正式提交引用的受控试验结果。作业到达冻结的最晚截止时仍无结果，服务端标 `failed`，迟到回执不得覆盖；学生可复用封存录音手动重试，不占有效次数。

### 短句同步、长录音异步的混合候选

- 保持所有录音 1 秒至 5 分钟均可上传；按**服务端实测可安全完成的时长阈值**选路径。例如先把 30 秒作为待验证的候选阈值：短句沿用现行单次 15 秒超时/自动重试，较长录音提交后立即返回作业 ID 并持续轮询。阈值不能只凭 Windows 样本固定，须在获授权的目标普通云函数配置下测冷/热 P95 与成本后决定。
- 同一 S-05 录音按钮、试听和重录不变，但评分按钮可能出现两种结果节奏：短句可在当前页完成，长录音进入可离页恢复的“处理中”。页面在评分前按服务端返回的路径解释预期，不靠客户端时长自行推断；任务提交按钮对未终态作业的处理仍须产品选择。
- 这条路线**不改变 5 分钟录音上限**，但长录音的单次后台执行若仍严格限 15 秒，当前近 5 分钟样本仍可能失败。要让长录音有可行性，需另审其后台执行上限（候选 30 秒）和用户可见最终等待上限；混合候选不能被描述为完全遵守原 15 秒评分时限。

## 与现行产品契约的明确差异

| 项目 | 已确认现行口径 | 候选需另审的口径 |
| --- | --- | --- |
| 单次时限 | 15 秒超时，自动重试一次 | **建议每次后台执行最长 30 秒**，全程最多两次；前台 `beginScore` 约 1—2 秒返回作业 ID。仅异步而仍设 15 秒不能解决约 5 分钟样本。30 秒也是估计，须 Linux 实测后冻结。 |
| 用户可见结果 | 一次等待后成功/低置信度/失败；录音保留 | `processing` 可跨页面/后台持续，约 70—90 秒到达最终失败截止（两次执行、队列及回执余量）；具体上限须实测并经用户确认。不得用“已受理”冒称“已评分”。 |
| 重试与有效次数 | 系统自动一次重试；最多五次有效分 | 作业内部重试一次；同作业/同录音/同操作 ID 幂等。只有 `scored` 且版本仍有效才消耗次数；人工重试先查旧作业终态，不能创建并行评分绕过上限。 |
| 提交锁定 | 提交后不再发起评分；退回按剩余次数 | 异步完成可能晚于提交。应在提交前要求所有必需评分作业达到终态，或将提交时仍在处理的作业锁定为 `superseded`；两种交互需产品选择，不能让迟到试验分回写已提交成绩。 |
| S-05 视觉状态 | 当前有生成中、成功、失败/重试 | 增加“已受理，仍在处理”、离开后返回的恢复状态、弱网轮询恢复和超时终态；沿用既有录音状态，不改已批准页图主体。新增状态板须单独视觉审阅。 |

## 调用量与最坏资源估计

- 单次学生尝试：录音 begin 1 次、封存 1 次、评分受理 1 次、Python 异步最多 2 次、受限完成入口最多 2 次，若每 2 秒轮询 90 秒则最多 **45 次只读查询**；总计最多约 **52 次函数调用**，其中 2 次为长时 1024 MB 推理。页面回后台即停止轮询，因此这是保守上界。
- 若每次 Python 实际运行 30 秒，两个任务最多约 **60 GB·秒**的推理计算资源，另加 Node、数据库、私有存储下载和流量；这是资源量估计，**不是账单或可用余额**。个人版的实际资源点/调用配额与超限政策须在目标环境读取，设置虚构账号及总调用数上限后才可试验。队列延时、重复投递和完成回执都可能增加实际调用，须用唯一作业 ID 去重但不能假定重投免费。
- 异步队列可靠性和最大等待时间须按 [SCF 异步调用机制](https://cloud.tencent.com/document/product/583/9694/) 实测；当前 `callFunction` 同步客户端能力不能直接证明事件派发可用。

## 最小 Linux 目标实测清单

1. 用户已明确当前只使用 Windows 与 D 盘缓存，**不安装或使用本地 Linux、WSL、Docker/Podman**。Linux x86_64 / Python3.11 / glibc 的 native `libvosk.so`、MP3 解码、模型加载、冷/热 RSS、解压及 `/tmp` 实测仅可在将来通过费用、安全和一次具体 M3 授权门槛后，在目标 CloudBase 普通云函数执行；本地静态 Linux wheel 包不能代替运行证据。
2. 用原创合成的 1 秒、短句、静音、加噪、接近 5 分钟样本各至少 10 次（含冷/热）测**下载私有录音→SHA→解码→推理→Node 回执落库**的全链路 P50/P95、最大时长和失败率；单独记录 Python 执行时间与队列等待。至少一组在拟定 1024 MB、无预热/额外付费的普通函数配置下执行。合成样本只验证性能，不证明儿童发音质量。
3. 只读核对目标套餐剩余额度、函数数量/包体/超时、函数安全规则与服务端 Event 异步调用权限；先在测试环境验证客户端直调拒绝、服务端签名、失效作业忽略、撤权和重复投递。未取得具体 M3 审阅包授权前，不创建/部署函数或修改规则。

**决定点**：若 Linux 30 秒单次后台执行与费用仍不可达，该异步候选同样不能放行；需另选可验证模型或经用户批准调整录音/评分时限。正式分数的儿童录音人工对照和 95% 成功率门槛仍独立保留。
