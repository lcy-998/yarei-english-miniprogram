# T-08 作答证据核对改进与非生产部署记录（2026-10-01）

## 原因与处理

教师反馈快速点评的“查看详情”只呈现页数、词数、题数及小字摘要，缺少能进入并翻阅的完整作答核对界面。原页面把服务端证据压成文本行，任务项还依赖另一次需要 `task.publish` 权限的任务预览；具备点评权限的教师不应依靠发布权限才能看到当前提交的任务内容。

按 0.39.0 基线，`review-query.getSubmissionForReview` 在原有教师与班级授权、提交版本校验之后返回发布快照中的任务项和指定阅读页，仅对该提交指定的云端页图签发短期地址。T-08 在同一点评流程内进入只读核对视图：阅读指定页可翻阅，单词显示逐次作答，习题显示题干、选项、学生答案、正确答案与解析，已开放录音任务沿用受控试听。退出核对视图保留评分、评语和队列位置；查看不会写入学生学习进度。旧提交未保存逐词或逐题证据时如实提示，不能由数量摘要还原答案。听力、看视频及跟读媒体仍属 M3。

## 实际验证

- 后端 `npm run check` 通过：96 个文件、594 项测试；新增用例验证只有检查权限的教师可按提交读取任务项和指定页，未选页不会返回，并验证私有页图签发。
- 小程序根 `npm run check` 通过：185 个文件、894 项测试；后台 11 个文件、49 项测试及构建通过。新增页面用例验证内容项、阅读页切换后返回点评保留未发布评分与评语。后续小范围修正后再次运行小程序和后端类型检查，均通过。
- 微信开发者工具 `compile_wxml` 对 T-08 返回 `success: true`，`simulator_open_page` 返回成功，控制台 `error` 过滤为空。当前缺少有效教师页面会话，**尚未完成已登录教师点按、页图显示、录音试听与真机人工验收**；路由编译不等于业务页面验收。
- 后端构建得到 38 个独立函数包；本次只部署 `review-query`，其他函数和数据库集合未改变。

## 非生产云端变更

部署前核对本机私有环境与项目配置一致，云端只有一个匹配环境，状态 `NORMAL`、个人版、未开启超额计费、未产生费用。原 `review-query` 为 `Active`、`Nodejs20.19`、10 秒、256 MiB、`index.main`、依赖安装启用且无触发器；发布不可变回退版本 `2`（`m2-review-evidence-predeploy-20261001`）。随后用 ZIP 模式更新该函数；为纳入兼容性修正再次更新同一函数，均返回部署成功。最终 `$LATEST` 仍为 `Active`，运行配置和无触发器状态不变；云端下载代码与本地最终构建包的 SHA-256 完全一致。未修改存储规则、其他函数、演示账号或既有任务/提交数据。

无认证 SDK 调用在获取业务响应前返回 `MISSING_CREDENTIALS`，只证明该调用未携带凭据；本次没有把它当成跨组织、撤权或已登录教师页面验证。上线前仍需用当前非生产虚构教师账号在 T-08 分别检查新习题、阅读/单词双内容、录音和无逐项证据的旧提交，并核对历史版本、返回后评语保留、失效页图及授权撤销场景。

## 同日补记：只有一位学生可点评的原因

教师反馈快速点评看起来只能给一名学生打分。对既有非生产验收包中“长颈鹿词汇练习”任务执行只读计数：目标关系 36 条，其中 `awaiting_review` 为 1 条、`completed` 为 0 条、`not_started` 为 35 条。T-08 的既有规则只把已有正式提交且待点评的学生列入队列，因此当前 1/1 是真实队列人数；不能为尚未提交的 35 人编造作答和成绩。

为使范围可理解，小程序 T-08 曾增加任务布置人数、待点评人数、已点评人数及其他没有待点评提交的人数说明，并短暂提供通向 T-17 的入口；该入口随后依用户要求移除。T-17 对未提交学生仍明确提示没有作业内容。该轮小程序 `npm run check` 通过：185 个文件、894 项测试，后台 11 个文件、49 项测试及构建通过；T-08 WXML 编译返回成功。已登录教师实际触控及真机仍待验收。

## 同日补记：移除入口并准备多人点评数据

用户明确要求移除“查看全班完成情况”入口，同时增加几名已提交的虚构学生以验收多人打分。T-08 已移除该按钮和导航处理器，保留简短的人数口径说明。

在既有非生产环境运行 `tools/run-m2-review-queue-fixture.mjs inspect`：项目与私有环境一致；环境 `NORMAL`、个人版、未开启超额计费且未产生费用；验收任务、36 条对象关系、36 名有效班级成员及原题目快照一致。固定三名虚构学员当时均为 `not_started`，没有已有提交。受控操作器使用当前 `TaskCoreService.submit` 的完成规则、事务、自动判分和幂等边界，为三人分别提交原题目答案“giraffe”“elephant”“giraffe”；不预填教师评分或点评。

首次 `apply` 的三次提交均成功，但操作器把业务提交 ID 误当数据库物理文档键，导致后续读回检查失败并以非零退出。修正读回键后，独立 `verify` 退出码 0：三人均为 `awaiting_review`，提交版本、学生归属、题目原始答案和正确/错误判定逐条一致；加上原有一份，该任务当时待点评共 **4 人**。教师 `getCompletion` 返回 36 条关系，`listTeacherTasks` 的当前任务待点评数为 4，`getSubmissionForReview` 可对三份新提交逐题读取证据。再次执行 `apply` 返回 `fresh:0;seeded:3`，未生成重复提交。新增数据仅属于 M2 虚构验收任务；没有删除 M1 数据、轮换密码、发布小程序或改动云函数。因该题同时是现有打卡活动的每日条件，本次提交可能计入提交当日的虚构打卡结果，验收榜单时应按实际证据核对。

多人点评需在已登录教师小程序页面重新编译后实际点选、评分和发布；本次服务端读回不替代该页面验收。随着教师逐份点评，待点评人数将相应减少。
