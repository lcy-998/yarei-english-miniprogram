# S-16 课堂录音上传校验修复

日期：2026-10-06  
页面：S-16 课堂录音任务

## 现象与代码检查

截图显示录音已计时 00:02，上传后进入“录音不可提交”，提示云端无法识别，并只显示重录操作。代码检查发现课堂录音服务强制按 MP3 解析并拒绝 AAC；项目媒体基线允许学生录音使用 MP3/AAC。截图本身不能证明该次文件实际编码，但此严格限制会把合法 AAC 文件误判为无效。

后续截图已显示更新后的“云端安全或音频校验未通过”提示，说明小程序端错误映射已更新，但提交仍收到 `MEDIA_INVALID`。当时非生产 CloudBase 仍运行旧版 MP3 强制解析；现已按用户授权更新单一函数并读回核对，部署详情见下文。

## 修复

- 云端封存器改为从文件内容读取格式，接受 MP3 和 AAC；封存文件按检测到的编码使用 `.mp3`、`.aac` 或 `.m4a` 扩展名。
- 任务录音服务契约接受两种已批准编码，仍保留 1 秒至 5 分钟、20 MB 和安全路径检查。
- S-16 云端校验失败时将录音和已上传的暂存文件 ID 留在本页，显示试听、重试封存和重录入口；重试复用同一暂存文件与幂等请求。提示涵盖安全或音频校验失败。服务暂时不可用时继续保留原来的可重试提示。
- 现有服务端无效编码回归用例改为使用不支持的 FLAC。

## 2026-10-06 再次失败的根因与修复

用户再次提供 S-16 的“云端安全或音频校验未通过”截图。核对发现，`TaskRecordingService.begin` 使用 `hashHex` 生成 **16 位**本人暂存目录，而 `CloudBaseTaskRecordingSeal.inspectAndSeal` 使用 SHA-256 生成 **64 位**目录并要求暂存路径与之相等。云端现存的近期暂存对象元数据确为 16 位目录、非空 MP3 类型；这项不一致会在读取音频内容之前固定返回 `MEDIA_INVALID`。此前仅扩大 MP3/AAC 编码接受范围无法修复该路径拒绝。

现将封存器的暂存路径校验改为与草稿签发一致的 `hashHex`；私有封存路径继续沿用 SHA-256，环境、组织、学生和录音 ID 的精确匹配不放宽。新增“创建草稿签发路径可直接封存”回归用例，另更新封存器的 MP3/AAC 和跨学生拒绝用例。没有下载、播放或保存用户录音内容。

在同一已授权非生产环境，仅对 `task-recording-command` 当前远端代码做上述两行精确修复并更新单函数代码。部署前包 `index.js` SHA-256 为 `0E4EA8D57C90CC6E690BB0E70732CB332111387DB573C822EF58D6A24927C889`；云端回读与目标包均为 `82307CE4F807F839FDCA0287E98171DCAC3A25BB02C90C51CA9A5FC84BC8F2ED`。函数回读为 `Active`、Nodejs20.19、512 MB、60 秒、无触发器、六个原有环境变量键；未改数据库、权限、旧媒体或其他函数。后端完整 `npm run check` 通过：153 个测试文件、801 项测试。

本轮没有用用户录音重新发起封存，也没有已登录微信模拟器或真机端到端通过证据。用户可在保留原页本机录音的情况下点击“重试上传”；若页面已关闭导致临时文件丢失，需要重新录制。实际成功状态还须以学生页显示“录音已上传”及随后正式提交为准。

后续复发已通过云端日志与用户许可的技术元数据定位为开发者工具模拟器生成 WebM/Opus，而非 MP3/AAC；转换修复及独立授权、部署记录见 [S-16 WebM/Opus 非生产审阅包](s16-webm-opus-nonproduction-review-2026-10-06.md)。本节此前“可重试即可能成功”的判断不适用于该模拟器编码。
