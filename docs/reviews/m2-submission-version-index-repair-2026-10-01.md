# M2 第二次退回失败：非生产提交索引修复记录（2026-10-01）

## 故障与原因

虚构任务“单独的测试”的当前学生关系为 `awaiting_review`，`redoCount=1`，最新提交版本为 2；产品规则允许第二次退回。当前第二次退回返回 `INTERNAL_ERROR`，失败后关系仍为待检查，最新提交仍为已提交，只有第一次退回的反馈记录。已部署只读查询可读取两次提交历史；本地内存 repository 可完成第二次退回。

对同一非生产数据执行强制中止的 CloudBase 事务诊断，写入不会提交，诊断前后关系版本、状态和反馈数相同。事务在更新第二份提交文档时收到 `DATABASE_REQUEST_FAILED`／`E11000 duplicate key`。现行 `submissions` 唯一索引 `uniq_assignment_version` 错用文档 CAS 字段 `version`：第一次退回把首份提交的文档版本升为 2，第二份提交再次退回也要把其文档版本升为 2，产生冲突。应使用不可变的业务 `submissionVersion` 作为唯一键。

## 预检与安全步骤

- 仅操作既有非生产环境的 `submissions` 索引；不删除、迁移或改写 39 条现存提交及其他 M1 数据。
- 只读对账确认当前 39 条提交的 `(organizationId, assignmentId, submissionVersion)` 组合全部唯一。现行集合有 `_id_`、`_openid_1`、错误的 `uniq_assignment_version` 和一个任务状态查询索引。
- 先创建 `(organizationId, assignmentId, submissionVersion)` 的新唯一索引；如果创建或核对失败，停止，不移除旧索引。
- 新索引确认后仅移除 `uniq_assignment_version`。若移除失败，两个索引可并存，数据不变；复核后再处理，不放宽业务权限或关闭任务校验。
- 修复后用相同任务做强制中止的第二次退回事务复测：必须到达成功回执且现有关系、提交、反馈仍完全不变。教师原本填写的退回原因不由测试脚本代填或提交。

本地机器可读清单及数据字典已改为 `submissionVersion`，新增回归断言防止再次把文档 CAS 版本作为业务唯一键。云端步骤的实际结果与未完成验证将在本记录续写。

## 实际执行与结果

执行前再次确认项目配置与本机私有配置指向唯一同一个非生产环境；环境 `NORMAL`、个人版、未开启超额计费、未产生费用。后端 `npm run check` 通过：96 个测试文件、594 项用例，静态类型检查通过。只读读取当前 39 条提交并核对业务提交唯一键无重复。

先创建 `uniq_assignment_submission_version` 唯一索引，字段按 `organizationId`、`assignmentId`、`submissionVersion` 顺序；云端只读复核为唯一索引，原索引仍在。随后仅删除错误的 `uniq_assignment_version` 索引。最终只读索引列表仍为 4 项：两个系统索引、正确的新唯一索引及原任务状态查询索引；错误索引已不存在。没有删除或更新任何提交、反馈、任务或账号文档，也没有部署函数、修改访问规则或存储规则。

修复后重跑同一份虚构作业的强制中止事务诊断，服务端第二次退回完整走到 `ok` 回执；脚本主动抛出诊断中止标识，数据库事务未提交。独立读回确认作业关系仍为 `awaiting_review`、`redoCount=1`、最新提交版本 2，第二份提交仍为 `submitted` 且没有新增反馈。此项证明导致失败的唯一索引冲突已消失；**教师在页面填写原退回原因并实际发布仍须重新操作验收**。用户历史失败操作没有成功写入，不存在重复退回或消耗第二次退回额度。
